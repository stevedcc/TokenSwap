# YubiKey through Yubico's SDK, stage 1: replace ykman, add `tswap yubikey setup` — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** tswap talks to YubiKeys only through Yubico's .NET SDK (no ykman anywhere), and `tswap yubikey setup` programs slot 2 itself, refusing anything that could lock a vault out.

**Architecture:** `IYubiKeyService` stays the seam. A new `SdkYubiKeyService` implements it over a small internal device seam (`IOtpKeys`), whose one real implementation wraps the SDK and whose fake drives the unit tests. `YkmanYubiKeyService` and the ykman text parsing are deleted. A new `yubikey` command adds `setup`, using two new service operations (slot 2 state, program slot 2).

**Tech Stack:** C# / .NET 10 NativeAOT, `Yubico.YubiKey` 1.18.1 (exact pin), xUnit (TswapTests), GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-04-yubikey-sdk-portable-design.md` (approved 2026-11-04; "Stage 1 (part A)", "Spike findings", "Constraints"). Spike code for reference: branch `design/yubikey-sdk`, `spikes/yubikey-sdk/` (Native.cs-style setup in `SpikeEnvironment.cs`, OTP calls in `Otp.cs`, device pick in `Devices.cs`).

## Global Constraints

- The OTP slot's crypto and blob format (`YubiKeySlotBlob` v1/v2, `YubiKeySlotKek`) do not change; existing vaults keep opening. Only the transport that obtains the HMAC-SHA1 response changes.
- The challenge bytes are exactly what ykman got: UTF-8 of the challenge string, truncated or zero-padded to 64 bytes (`YkmanYubiKeyService.ChallengeReportingTouch` today), sent to slot 2 (`Slot.LongPress`) as HMAC-SHA1 (`UseYubiOtp(false)`).
- No fallback to ykman, anywhere (design anti-goal). After this plan, `ykman` appears in `TswapCli/` and `TswapCore/` only inside the migration note text named in Task 3.
- `Yubico.YubiKey` is referenced as `Version="[1.18.1]"` (exact pin, like BouncyCastle's) in `TswapCore/TswapCore.csproj`.
- NativeAOT publish has zero IL2xxx/IL3xxx warnings (spike: 0).
- Linux: `libpcsclite.so.1` is used when present and never required (owner, 2026-11-05; design "Constraints"): the binary has no `NEEDED` entry for it and starts and works without it.
- The SDK's own logging never reaches the user's terminal (the spike printed `fail: Yubico.Core...` lines on macOS).
- `TestKeyYubiKeyService` and `SimulatedYubiKeyService` keep their behaviour; tests using them don't change except where a task says so.
- `tswap yubikey setup` never needs sudo, never writes the vault, and only ever touches slot 2.
- File ownership while the docs restructure (#244, branch `docs/restructure`) runs: this branch does not edit `README.md` or `docs/` (except its own design and plan) until Task 6, which first merges `main`.
- Hardware rule (design, "Hardware for testing"): the owner has no spare key; automated hardware tests only list, challenge and read slot state, with one exception, the spare-key test (Task 2), which programs a key the owner has named as spare and refuses the main key's serial. Programming is otherwise tested against the fake; the owner checks on real hardware later.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; no session links.

## Review Focus

1. **Two processes at once (#173):** a second tswap call while the key is busy (a touch pending in another terminal). Expected: a clear "the YubiKey is busy (another tswap or app is using it); try again" error naming the serial, not "No YubiKey detected". Pinned by Task 2's `ListSerials_KeyBusy_SaysBusy` and `Challenge_KeyBusy_SaysBusy`, unless Task 2's busy contingency rules them out (then reported unmet).
2. **A key the OS hides from the keyboard interface** (at unlock too: `Challenge` checks first) (macOS without Input Monitoring; Linux without the udev rule): the key is visible over FIDO HID only. Expected: the per-OS explanation (today's `YubiKeyAccess` texts), not "no YubiKey found". Pinned by Task 2's `ListSerials_NoKeyboardReachableKey_ExplainsPerOs`.
3. **Slot 2 not programmed:** expected "slot 2 of YubiKey N isn't set up for challenge-response; run `tswap yubikey setup`", at enrolment and at unlock. Pinned by Task 2's `Challenge_Slot2Empty_PointsToSetup`.
4. **A slot programmed by `tswap yubikey setup` must answer like one programmed by `ykman otp chalresp --generate`:** same flags (HMAC-SHA1, `HMAC_LT64` on, touch per flag). The key always receives a 64-byte frame; with `HMAC_LT64` it strips the trailing bytes equal to the frame's last byte before the HMAC, so for tswap's zero-padded challenges the flag changes the response. The settings are pinned by Task 4's `Setup_ProgramsYkmanCompatibleConfig` (the pure settings, with cited sources), and the bytes `ProgramSlot2` sends are proven in software: tswap builds the configure command itself (`YubicoOtpKeys.BuildSlot2Command`), and `Setup_Slot2CommandApduMatchesYkman` checks its APDU (Ins 0x01, P1 0x03 for slot 2, the data) against yubikey-manager 5.9.2's own builder output for a known key, with and without touch (Task 4 review fix round). Only the firmware's handling of those bytes needs hardware: Task 6's spare-key check `SpareKey_ProgrammedSlotMatchesYkmanSemantics` (known key, response against a software HMAC of the stripped challenge). Until a spare key exists, the release notes say that the firmware side is unchecked on hardware.
5. **`--replace` on the vault's only way in**, including a classic pair vault (refused), and a vault tswap can't read (proceeds with a warning, design). Pinned by Task 4's `Setup_Replace_*` tests.

The agent is never used to prove this key's slots or the password; the touch-count line comes after the prompt and before the first challenge), classifying each answer: opens; **definite wrong answer** (the key answered, the unwrap failed); **no usable answer** (busy, unplugged, touch timeout); and **slot 2 empty** (a `ProgramFailed` setup can leave it so), which aborts with the slot-2-empty text pointing at `tswap yubikey setup`, writing nothing (`SlotAdd_Slot2Empty_PointsToSetup`). Any "opens" → refuse as today ("YubiKey N already has a working slot"; this wins over any other answer). Otherwise any "no usable answer" → abort with the exact busy, timeout or unplugged text and write nothing. A key whose only slots are legacy pair slots is not a re-enrolment: `slot add` treats it as today (first enrolment of a one-key slot, which the pair rule already allows), and nothing labels a pair slot. Only when every one of its slots gives a definite wrong answer is this a **re-enrolment**: unlock the vault through the usual unlock path with this serial's one-key slots excluded (another plugged-in YubiKey, a legacy pair slot whose two keys are both plugged in, the machine's TPM or Secure Enclave, a running agent that holds the vault key, or `--recovery-key-stdin`), enrol a new slot for the key exactly as a first enrolment does (double challenge, touch posture from the first challenge, the vault password if the slot gets one), and write the keyring once. Output: "YubiKey N re-enrolled as a new slot (fingerprint ...); its old slot(s) no longer open and are kept (`tswap slots` lists them as other slots of this key)." With no other way in, refuse and name the ways (another key, a legacy pair slot with both its keys plugged in, the chip, the agent, `--recovery-key-stdin`).
- **Dead slots are not deleted.** Keyrings merge as a union (`vault merge`, `slot merge`), so a deleted slot would come back from another copy. Instead, this machine remembers, per serial, the slot that last opened the vault (and the one just enrolled at re-enrolment) in a separate small file, `yubikey-slots.json` (read and written by a new `TswapCore/Vault/RememberedYubiKeySlots.cs`, used by VaultUnlocker, `slot add` and setup's check), in the config folder (`TSWAP_CONFIG_DIR` or the default `~/.config/tswap`, the folder `config.json` lives in, not the vault folder, so it never travels with a synced or copied vault folder), keyed by the keyring's vault id (`Keyring.VaultId`) and the serial (so another vault's entry can't be mistaken for this one's); never merged; the keyring, config.json and blob formats don't change. It is a hint, not state: written atomically after the keyring write succeeds, through the same owner-preserving write path the config folder uses (under sudo the config folder is the invoking user's, as for `config.json`, and the file stays owned by that user, mode 0600, never root:root; on Windows the elevated process writes it with the same ACL as `config.json`); if it is missing, unreadable, malformed or root-owned, unlock ignores it and uses keyring order, never fails (`RememberedSlot_UnreadableMalformedOrRootOwned_UnlockStillWorks`, `SlotAdd_Reenrol_UnderSudo_RememberedFileKeepsOwner`). Unlock tries that slot first, so a re-enrolled key opens with one challenge; it then **continues past** a slot of the same serial that answers wrongly (one more challenge, possibly one more touch), and stops on a touch timeout with the usual message. `tswap slots` shows a serial's other slots as "another slot of this key (not the one it last opened with)" (not "dead", not "older": it can't know either without a challenge, and merges can bring in newer slots). On a machine that hasn't remembered yet, the first unlock may cost one extra challenge.
- `tswap yubikey setup --replace`'s check of another key (Task 4) also tries that key's remembered slot first (this task wires it; test `Setup_Replace_TriesRememberedSlotFirst`, call log).
- The hint is written after a successful unlock too (the slot that opened, per serial), through the same owner-preserving atomic path; a failed hint write never fails the unlock (`Unlock_HintWriteFails_UnlockStillSucceeds`, e.g. a root-owned hint file under a non-elevated unlock), nor a re-enrolment whose keyring write succeeded (it reports success and a one-line note; `SlotAdd_Reenrol_HintWriteFails_StillSucceeds`).
- Touches: the liveness check challenges the key once per existing slot, and enrolment twice more; the text before it says how many touches to expect for a touch key, computed from the actual slot list (never a fixed number).
- Only one-key slots are remembered: an unlock through a legacy pair slot writes no hint, and `tswap slots` marks nothing for pair slots. The remembered slot is per serial on this machine; a stale entry (another vault, a later reprogram) costs one extra challenge and unlock continues. Concurrent writers: last one wins (it's a hint). With nothing remembered, `tswap slots` marks nothing.
- What conversion leaves (RecordMigration): a classic XOR two-key vault becomes one one-key slot per key plus a recovery slot; a legacy pair keyring vault (pre-0.2 keyring with a pair slot) is left as it is. So the guide, for a legacy pair keyring vault, first enrols each key as a one-key slot (`sudo tswap slot add --yubikey` with both keys plugged in, one key at a time; a first enrolment, which the pair rule allows), and only then the touch upgrade below.
- The guide (`tswap migrate`'s plain-migrate guide) and the keyring note in MigrateCommand, and SecurityWarnings' no-touch advice, use this flow: per key, one at a time, with another way in available: `tswap yubikey setup --replace --touch --serial N`, then `sudo tswap slot add --yubikey`, then `tswap names` with only that key plugged in; then the next key. `recover --yubikey` is named only as the fallback when no other way in exists.
