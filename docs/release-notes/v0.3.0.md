# tswap v0.3.0

Draft: the YubiKey work (stage 1: the SDK and `tswap yubikey setup`; stage 2: FIDO2 slots) and
faster Linux TPM unlocks (an ECC P-256 primary for new slots). Later v0.3.0 work adds its own sections.

tswap now talks to a YubiKey itself, through Yubico's .NET SDK built into the binary, so `ykman`
is no longer needed. A new command, `tswap yubikey setup`, prepares a key's slot 2, and
`slot add --yubikey` enrols a reprogrammed key again through another way into the vault. A
YubiKey can also open a vault through a **FIDO2 slot**: the key's FIDO2 PIN and a touch on every
unlock, the same on Linux, macOS and Windows, and on a Mac without Input Monitoring.

## YubiKeys without ykman

- **No ykman, no Python.** tswap uses Yubico's .NET SDK (pinned at 1.18.1), compiled into the
  native binary. Every message that used to tell you to run `ykman` now names
  `tswap yubikey setup`; the `--help` prerequisites say the same.
- **Existing keys and v0.2 keyring vaults stay as they are.** tswap sends a key the same 64-byte
  challenge as before (the challenge string, truncated or zero-padded), so a slot 2 programmed with
  `ykman otp chalresp` is used as it is, with no re-enrolment. Measured on one Linux machine with
  one key (2026-11-05): the SDK's response matched ykman's (`./runtests.sh --yubikey`), and a vault
  made by v0.2's ykman-based build (`init --yubikey`) opened with this build. A classic single-file
  vault still needs `sudo tswap migrate --to-records` first, as in v0.2.0.
- **Faster unlocks.** Measured on the same machine and key, on one vault (`redact`, a YubiKey slot
  without touch, 3 runs each): 1.00-1.08 s with the ykman-based build, 0.44-0.52 s with this one,
  about twice as fast. The ykman-based build started up to three Python processes per unlock.
- **Errors name the real cause** instead of "No YubiKey detected":
  - a key another tswap or app is using (for example one waiting for a touch in another terminal):
    "A YubiKey is busy ...; try again when it's done";
  - a key whose OTP interface the OS hides: on Linux, the missing YubiKey udev rule (there is no
    smart-card fallback for this slot type); on macOS, Input Monitoring for the app running tswap;
  - a key whose slot 2 isn't set up: it points to `tswap yubikey setup`.
- **Touch detection** comes from the SDK's report that the key is waiting for a touch, instead of
  parsing ykman's output. A configured slot's touch setting still can't be read from the key, so it
  is learned from a challenge, as before. Not yet checked on a real touch key (below).
- **Linux:** the YubiKey udev rule is still needed for a normal user (it is what gives access to the
  key's hidraw device). tswap loads `libudev.so.1` itself, so the `libudev.so` link Yubico's docs
  ask for is not needed. `libpcsclite` is used if it is installed and is not needed (below).

Where each OS stands: [install.md](../install.md#yubikey-prerequisites) and
[portable.md](../portable.md#yubikeys).

## `tswap yubikey setup`

```bash
tswap yubikey setup --touch        # or --no-touch; one of the two is required
tswap yubikey setup --touch --serial N
```

It programs slot 2 for HMAC-SHA1 challenge-response with a new random secret, with the same flags
as `ykman otp chalresp --generate` (touch as asked), then challenges the key once to check that it
answers as set up. It needs no sudo and never writes the vault.

Programming slot 2 replaces what was there, so a vault slot made with the old secret stops opening
the vault. That is why `tswap yubikey setup` refuses an occupied slot without `--replace`, and
changes nothing. With `--replace` you type the key's serial at a terminal, and setup refuses when
the vault tswap is pointed at would be left without a way in that doesn't need this key: a TPM,
Secure Enclave or recovery slot counts, or another YubiKey's slot, if that key is plugged in and its
slot opens the vault now. A classic two-key vault that uses the key is always refused. A vault tswap
can't read gets a warning, and setup goes on. An empty slot 2 is programmed without the typed serial
or the vault check, `--replace` or not.

The check keeps the vault from being lost outright, not you from being stuck on one machine: setup
can't tell whether you still hold the recovery key, or whether a TPM or Secure Enclave slot belongs
to this machine or another one. Before `--replace`, make sure you have a way in that you can use
there. Only the vault tswap is pointed at is checked; the key's slots in other vaults die too.

Details: [Preparing a YubiKey](../setup.md#preparing-a-yubikey).

## Enrolling a reprogrammed key again: `slot add --yubikey`

Before, a key whose slot 2 was reprogrammed could only come back through `recover` and the recovery
key. Now `sudo tswap slot add --yubikey` does it with any other way into the vault:

- With every plugged-in key already enrolled, it asks which key to enrol. It reads slot 2 first (an
  empty slot 2 points to `tswap yubikey setup`), then challenges the key against each of its slots.
  A key with a working slot is refused as before; a busy key, or one that doesn't answer, stops it.
  Only when every slot answers wrongly is the key enrolled again, as a new slot, after the vault is
  opened another way: another enrolled YubiKey, this machine's TPM or Secure Enclave slot, a
  running `tswap agent`, or the recovery key with `--recovery-key-stdin`
  ([the appendix](../multi-machine.md#appendix-adding-a-key-with-the-recovery-key)).
- The dead slots are kept (keyrings merge as a union, so a removed slot would come back from
  another copy). This machine remembers the key's new slot and tries it first at unlock.
- **The vault password is asked at most once.** When a step is known to need it (one of the key's
  slots, or the new slot), it is asked before any challenge. Otherwise it is asked only if the
  unlock needs it, which is after the key's liveness challenges: still one prompt. The password
  typed before the checks is always compared with the vault's password verifier before anything is
  written: a mismatch always stops the command with nothing written, whether or not the new slot
  is to get the password.
- The new slot goes only into the vault it is enrolled in. Reprogramming kills the key's slot in
  every copy, so a machine with its own copy of the vault needs the slot merged in (through another
  way in there) before the key opens it again.

The touch upgrade now uses this flow, one key at a time:
`tswap yubikey setup --replace --touch --serial N`, then `sudo tswap slot add --yubikey`, then
`tswap names` with only that key plugged in. A 0.1 pair keyring vault first gives each key its own
slot with `slot add --yubikey`. `tswap migrate`'s guide and the no-touch notice print these steps; `recover --yubikey` is only the
fallback. Details: [YubiKey: touch or no touch](../security-model.md#yubikey-touch-or-no-touch).

## FIDO2 slots

A new slot kind, made with `tswap init --fido2` or `sudo tswap slot add --fido2` (and offered by
the guided `tswap init`): a FIDO2 credential on a YubiKey, opened through the hmac-secret
extension. Details: [setup.md, FIDO2 slots](../setup.md#fido2-slots).

- **Why:** a key's OTP slot needs Input Monitoring for the terminal on a Mac, which lets every
  program the terminal runs read keystrokes. The FIDO interface isn't a keyboard, so a FIDO2 slot
  needs no Input Monitoring. It is designed to work the same on Linux, macOS and Windows, so that a
  slot made on one OS opens on the others. Verified so far: a spike in which one credential gave
  the same output on Linux and Windows. macOS, and the cross-OS directions with this build, are
  still to check (below).
- **The key's FIDO2 PIN and a touch on every enrolment and unlock**, on every OS; there is no
  PIN-free mode. On Linux and macOS tswap asks for the PIN at the terminal (`/dev/tty`, no echo, so
  `--recovery-key-stdin` works alongside); on Windows, Windows' security key dialog asks, owns PIN
  entry and may ask again after a wrong PIN within one unlock.
- **PIN tries are protected.** tswap never retries a wrong PIN, shows the tries left (a key allows
  8 wrong PINs in all; after 3 in a row it must be re-inserted), and tries FIDO2 slots last, after
  every slot that needs no PIN, the agent and the vault-password prompt. On Linux and macOS it
  first checks silently which plugged-in key holds a slot, so an unplugged key costs no PIN.
  tswap never changes an existing PIN and never resets a key; a key without a FIDO2 PIN is offered
  one at enrolment (Linux and macOS; on Windows the dialog asks).
- **No terminal, no FIDO2.** Scripts, CI and agents skip FIDO2 slots without a key call or a
  Windows dialog, and an enrolment without a terminal is refused. `broker serve` refuses a machine
  whose own slot is FIDO2: a broker needs a TPM or Secure Enclave own slot.
- **A FIDO2 reset kills the slot**, as reprogramming slot 2 kills an OTP slot: the unlock says so
  ("a FIDO2 reset deleted it") rather than reporting a wrong PIN, and the key is enrolled again
  with `slot add --fido2` through another way in.
- **YubiKeys only for now**, identified by Yubico's published model ids (AAGUIDs): the YubiKey 5,
  Bio and Security Key series. FIDO-only keys (Security Key, Bio) are supported, shown by model
  when they report no serial, but not yet tested on hardware. Other brands are refused, naming
  [#193](https://github.com/stevedcc/TokenSwap/issues/193).
- **`tswap slots`** lists `YubiKey N, FIDO2: PIN + touch, ...`. `tswap yubikey setup --replace`
  counts a FIDO2 slot as a way in only if it opens now (its PIN and a touch). Guided `init` offers
  each key as an OTP slot and a FIDO2 slot (on a Mac the FIDO2 slot first), and an OTP enrolment
  ends with a hint to add a FIDO2 slot for use on a Mac.
- **Older tswap versions refuse a FIDO2 slot clearly.** The slot's blob is the YubiKey blob's
  version 3 ([hardware-backends.md](../design/hardware-backends.md#yubikey-fido2-slots-v030-issue-193)),
  so for that slot v0.2.x reports `Slot <id8>:` followed by `needs a newer tswap (blob version 3
  or unknown flags); upgrade tswap.`, and still opens the vault with its other slots. A vault made by `init --fido2` needs v0.3.0
  on every machine that opens it with that slot.
- **Every message** is in the build: wrong PIN with the tries left, re-insert, blocked, the key
  not plugged in, a reset key, a non-YubiKey, no terminal, a busy key, Windows' WebAuthn API too
  old (it needs version 4).

## Linux TPM: faster unlocks (ECC P-256 primary)

Every Linux TPM unlock rebuilds the TPM's storage primary key, and generating the RSA-2048 one was
most of the unlock. New Linux TPM slots (`init --tpm`, `slot request --tpm`, `recover --tpm`) seal
under an ECC P-256 primary instead. Generating the primary alone, measured with
`tpm2_createprimary`: 1.74 s → 0.26 s on an Intel PTT, 8.2 s → 0.63 s on an Infineon SLB 9665.
Whole unlocks of an ECC slot on both chips: Task 3, to be filled from real-hardware runs.

- **Protection unchanged.** Both primaries protect the sealed object with AES-128-CFB; only the
  primary's key type changes. The primary is still never stored.
- **`tswap slots`** shows a new slot as `TPM (ECC P-256), sealed to this machine's TPM, …`. Every
  other TPM row keeps its text (`TPM, sealed to this machine's TPM, …`): those are the RSA-2048
  slots on Linux and every Windows TPM slot, which tswap can't tell apart from the blob.
- **Existing slots stay RSA-2048 and keep working.** Nothing is converted. How to replace an existing
  slot with a fast one: to be decided (the planned `slot add` + `slot remove` doesn't exist: `slot
  add` enrols YubiKeys only, and there is no `slot remove`).
- **Older tswap versions refuse a new slot clearly.** A new slot's blob has the `TSTP` header with
  flag bit 1 (`0x02`, or `0x03` with the vault password), which v0.2.x doesn't know, so for that slot
  it says `needs a newer tswap (blob version 1 or unknown flags); upgrade tswap.` before it touches
  the TPM, and still opens the vault with its other slots. Every machine that opens the vault with that slot
  needs v0.3.0.
- **Windows** is unchanged: its TPM key is made once at enrolment, so an unlock generates no key.
- The text for a damaged slot header now reads `a header with no known flag, or a truncated blob or
  trailing bytes (corrupt); restore config.json from backup.`
- Removing a new slot's header by hand gets the generic "Could not unlock with the TPM" text instead
  of the stripped-header one; it fails closed either way
  ([hardware-backends.md](../design/hardware-backends.md#storage-primary-ecc-p-256-for-new-slots-v030-issue-261)).

## Linux: `libpcsclite` is optional

The SDK links the PC/SC (smart-card) library; tswap replaces that link with a small loader of its
own, so the binary has no `libpcsclite` dependency. At the first PC/SC call it opens
`libpcsclite.so.1` if it is there and forwards to it; if it isn't (or lacks any of the 11 functions),
a stand-in answers "no smart-card service" and the SDK finds keys over USB HID only.
`tswap -v yubikey setup --touch` (or `--no-touch`) prints which one was used. On a key whose slot 2
is empty that command programs it, so check with a configured key (setup then refuses) or with
`--serial 2147483647`, a serial no key is expected to have, as the smoke test does.

What the evidence proves:

- **The binary starts without the library.** The release smoke test checks that the binary has no
  `NEEDED` entry for `libpcsclite`, and, where `bwrap` can make a sandbox (it prints `SKIP` where it
  can't), runs it once with the library hidden.
- **A key works without the library.** On a Linux machine with a key plugged in, the build with the
  library hidden chose the stand-in, found the key over its OTP (keyboard) interface and read its
  slot 2: the run ended at setup's refusal of an occupied slot, as expected. That run sent no
  challenge and programmed nothing.
- **Forwarding works as far as listing goes.** With the library present, the same run chose the
  system library and also found the key over smart card, which goes through the forwarded calls
  that open a PC/SC context, list the readers, wait for a reader's state and connect. tswap has no
  smart-card feature, so a mistake in a forwarder that listing doesn't use would stay unnoticed
  until one exists.

## Binary size

The SDK adds about 6.7 MB: the Linux x64 binary goes from 15.6 MB (15,580,432 bytes) to 22.3 MB
(22,252,272 bytes). Other platforms were not measured.

## Not yet verified on real hardware

- **Programming slot 2** (`tswap yubikey setup` on an empty slot, and `--replace`) has been tested
  against a fake device only. The command it sends is checked in software against yubikey-manager
  5.9.2's own builder, for a known key with and without touch. How the key's firmware handles it is
  unchecked until the owner's spare-key test (`SpareKey_ProgrammedSlotMatchesYkmanSemantics`) runs.
- **Touch, with a key that requires one:** that tswap detects and records a touch-required key's
  posture through the SDK, and that `tswap yubikey setup --touch`'s check challenge asks for the
  touch. The runs on a real key so far used a key without touch.
- **Read-only checks still to do on a real key** before release (owner): `tswap names` against a
  YubiKey slot on macOS (with Input Monitoring) and Windows, setup's refusal of a configured slot
  there, and the busy message for a second `tswap names` while the first waits for a touch.
- **Done on a real key so far** (read-only, one Linux machine, one key): the responses match
  ykman's; a vault made by the ykman-based build opens with this one; the unlock timing above;
  setup's refusal of a configured slot 2, with the PC/SC library present and hidden (above).
- **FIDO2 slots: nothing of this build has run on a real key yet.** Every path is tested against
  a fake device. What a 2026-11-06 spike showed on the owner's key (a YubiKey 5 NFC): a NativeAOT
  build on Windows 11 made a non-discoverable hmac-secret credential through `webauthn.dll` and got
  the same 32-byte output twice, and the same credential gave the same output on Linux through the
  SDK with PIN and touch. Still to run, by the owner, before release
  ([the runbook](../superpowers/fido2-owner-checks.md)):
  - enrol and unlock on Linux through this build's raw SDK path, then the same vault on macOS and
    Windows, and slots made on each OS opened on the other two;
  - two FIDO2 slots (two keys) in one Windows dialog, each key in turn (the per-credential salt list
    has never run), and NFC on Windows if a reader is available;
  - the Windows results that are mapped from documentation only: the HRESULT when the key picked
    holds none of the vault's credentials, and an already-enrolled key at enrolment (`NTE_EXISTS`);
  - the terminal PIN prompt on Linux and macOS: no echo, echo back after Enter, `Ctrl+C`, `Ctrl+Z`
    then `fg`, and `Ctrl+\`;
  - guided `init` on each OS, and `yubikey setup --replace` with a FIDO2 slot;
  - on a spare key only: wrong-PIN counts and the re-insert after three, a key without a FIDO2 PIN
    (Linux, macOS and Windows), and a FIDO2 reset reported as a dead slot;
  - a non-YubiKey (a Token2) refused cleanly on every OS;
  - a FIDO-only key (Security Key or Bio), if one is available.
